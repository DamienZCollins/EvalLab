# EvalLab 总体方案

> 独立的 Agent 离线评测平台，提供从 Trace 采集到回归门禁的完整闭环

## 1. 项目定位

- 核心亮点：
  1. 完整 Trace 采集：两层模型（trace > span），支持嵌套和工具调用链
  2. 多维度自动评分：规则评分 + 工具调用评分 + LLM-as-Judge
  3. 失败归因分层：5 层自动归因（输入理解/规划/工具调用/输出生成/数据环境）
  4. Judge 校准体系：人工抽检对照组，计算 Judge 准确率和归因准确率
  5. 回归门禁：基线对比 + 阈值判断，指标退化时拦截 CI（退出码 1）

- 明确不做：
  - Prompt 管理仓库（中心化版本控制）
  - 生产监控和实时告警
  - 多租户和复杂权限
  - 通用可观测平台对接

## 2. 领域建模

### 核心对象

- **Trace**：一次 Agent 任务执行的完整记录
  - 包含：任务输入/输出、状态、总耗时、总 token
  - 关联：多个 Span

- **Span**：单次工具调用或 LLM 调用
  - 包含：工具名称、输入/输出、耗时、token、错误信息、事件日志
  - 支持：父子嵌套关系
  - 类型：LLM_CALL / TOOL_CALL / RETRIEVAL

- **用例（TestCase）**：评测输入和期望
  - 包含：输入指令、期望类型（`match_type`）+ 期望输出、期望工具序列、故障注入参数、标签、分组
  - 支持：版本管理、启用/禁用
  - 字段定义见 [设计决策 D3](设计决策.md#d3-用例的规则字段)

- **评测任务（EvalTask）**：一次批量评测
  - 包含：被测 Agent、用例筛选条件、执行状态、统计指标
  - 关联：多个评测结果、可选基线

- **评测结果（EvalResult）**：单个用例的执行结果
  - 包含：关联 Trace、通过/失败状态、失败原因、失败分层
  - 关联：多个评分记录

- **评分（Score）**：单个维度的评分
  - 类型：RULE（规则）/ TOOL_CORRECTNESS（工具调用）/ LLM_JUDGE（Judge）
  - 包含：评分名称、分数（0-1）、评分理由

- **基线（Baseline）**：历史评测的快照
  - 包含：通过率、平均分、P95 耗时
  - 用于：回归对比

- **人工抽检（ManualReview）**：Judge 和归因的校准数据
  - 包含：人工评分、人工失败分层、对应的 Judge 评分和系统归因
  - 用于：计算准确率

### 状态流转

**评测任务**：
```text
PENDING -> RUNNING -> COMPLETED / FAILED
```

**评测结果**：
```text
PASS / FAIL
```

**Trace**：
```text
SUCCESS / FAILED / TIMEOUT
```

## 4. 数据设计

### 核心表

| 表 | 职责 | 关键约束/索引 |
|---|------|--------------|
| eval_trace | Trace 主记录 | trace_id 唯一，idx(agent_name, created_at) |
| eval_span | Span 记录 | span_id 在同一 trace 内唯一（uk `<trace_id, span_id>`），idx(trace_id)，idx(parent_span_id)，events 存 JSON |
| eval_testcase | 评测用例 | testcase_id 唯一，idx(group_id)，idx(version) |
| eval_testcase_group | 用例分组（单层） | group_name 唯一 |
| eval_task | 评测任务 | task_id 唯一，idx(agent_name, created_at) |
| eval_result | 评测结果 | result_id 唯一，idx(task_id)，idx(failure_category) |
| eval_score | 评分记录 | idx(result_id)，idx(scorer_type) |
| eval_baseline | 基线快照 | baseline_id 唯一，idx(agent_name) |
| eval_manual_review | 人工抽检 | result_id 唯一 |
| eval_redteam_case | 红队用例（加分项） | redteam_case_id 唯一，testcase_id 唯一，idx(attack_type) |

### 关键设计

- **Trace 两层模型**：trace > span，events 并入 span JSON，简化查询
- **用例分组单层**：避免树形结构复杂度，group_id 直接关联
- **评分 0-1 量纲**：统一评分标准，便于对比和校准
- **人工抽检字段**：同时存储人工评分/分层和 Judge 评分/系统归因，计算准确率
- **用例期望声明**：单一 `match_type` 决定规则评分语义，`expected_tools` 独立声明工具序列，`fault_injection` 随用例下发（见 [D3](设计决策.md#d3-用例的规则字段)）
- **结果可复现**：`eval_result` 记录 `testcase_version` 快照，用例后续编辑不影响历史结果

## 5. Agent 接入契约

> 接入流程的主次见 [设计决策 D1](设计决策.md#d1-两个接入流程的主次)：**平台拉取 `/execute` 是主路径**，`POST /api/trace` 上报是补充路径，上报的 Trace 不参与评测。

### 平台调用 Agent（主路径）

**请求**：`POST /execute`
```json
{
  "task_id": "uuid",
  "case_id": "uuid",
  "input": "用户指令",
  "fault_injection": {
    "type": "TOOL_ERROR | STEP_MISSING | OUTPUT_FORMAT_ERROR | TIMEOUT | INPUT_MISUNDERSTAND",
    "target_span": "span 编号 | null"
  }
}
```

`fault_injection` 来自用例配置，普通 Agent 忽略该字段。

**响应**：
```json
{
  "trace_id": "uuid",
  "agent_name": "fault-injection-agent",
  "status": "SUCCESS | FAILED | TIMEOUT",
  "output": "Agent 最终输出",
  "total_tokens": 1234,
  "duration_ms": 5678,
  "spans": [
    {
      "span_id": "uuid",
      "parent_span_id": "uuid | null",
      "span_type": "LLM_CALL | TOOL_CALL | RETRIEVAL",
      "tool_name": "工具名 | null",
      "input": "输入参数",
      "output": "输出结果",
      "error": "错误信息 | null",
      "tokens": 100,
      "duration_ms": 234,
      "start_time": "ISO 8601",
      "end_time": "ISO 8601",
      "events": [
        {
          "event_type": "LOG | ERROR | WARNING",
          "message": "日志内容",
          "timestamp": "ISO 8601"
        }
      ]
    }
  ]
}
```

### 故障注入 Agent（验证用）

实现同一套 `/execute` 契约，额外读取 `fault_injection` 制造确定性故障。

**请求**（与主路径一致）
```json
{
  "task_id": "uuid",
  "case_id": "uuid",
  "input": "用户指令",
  "fault_injection": {
    "type": "TOOL_ERROR | STEP_MISSING | OUTPUT_FORMAT_ERROR | TIMEOUT | INPUT_MISUNDERSTAND",
    "target_span": "span 编号 | null"
  }
}
```

**故障类型**：
- `TOOL_ERROR`：工具调用返回错误
- `STEP_MISSING`：跳过某个规划步骤
- `OUTPUT_FORMAT_ERROR`：返回不符合格式的输出
- `TIMEOUT`：模拟超时
- `INPUT_MISUNDERSTAND`：故意曲解用户指令

## 6. 接口设计

### Trace 采集

- `POST /api/trace`
  - 入参：完整 Trace JSON（Agent 执行后上报）
  - 出参：`trace_id` 与 `duplicated`（true 表示该 trace_id 已存在、本次未写入）
  - 说明：**补充路径**。存储到数据库并解析 span 关系；`trace_id` 幂等，已存在时返回原 ID 不覆盖；上报的 Trace 不参与评测（见 [设计决策 D1](设计决策.md#d1-两个接入流程的主次)）

### 用例管理

- `GET /api/testcase`：查询用例列表（`group_id` / `tag` 筛选，`enabled_only` 默认 true）
- `GET /api/testcase/{id}`：用例详情
- `POST /api/testcase`：创建用例
- `PUT /api/testcase/{id}`：更新用例（`version` +1）
- `DELETE /api/testcase/{id}`：删除用例
- `GET /api/testcase/group`、`POST /api/testcase/group`：分组列表 / 创建

### 评测任务

- `POST /api/eval/task`
  - 入参：agent_name、`group_id` / `tag`（筛选条件，均可空，只取启用用例）
  - 出参：完整任务对象（含 task_id 与状态）
  - 说明：创建评测任务，异步执行；基线不在此绑定，门禁时再指定 `baseline_id`
- `GET /api/eval/task/{id}`：查询任务状态和统计
- `GET /api/eval/task/{id}/result`：查询该任务的全部结果，含每例的评分记录与失败归因

### 基线管理

- `POST /api/baseline`
  - 入参：task_id（从某次评测创建基线）
  - 出参：baseline_id
- `GET /api/baseline`：查询基线列表
- 基线快照含 `agent_name`、`total_cases`、通过率、平均分、P95；同一任务只能建一条基线；与当前任务 Agent 不同时门禁结果标 `cross_agent`

### 回归门禁

- `POST /api/eval/gate`
  - 入参：task_id、baseline_id、阈值配置
  - 出参：通过/失败、变化详情
  - HTTP 状态码：通过 200，失败 422
- **命令行工具**：`java -jar cli/target/cli.jar --task <task_id> --baseline <baseline_id> [--threshold-* ...]`
  - 退出码：0（通过）/ 1（回归）/ 2（参数错误或请求失败）
  - 输出：变化详情（表格）

### 人工抽检

- `POST /api/manual-review`
  - 入参：result_id、人工评分、人工失败分层、评语；同一 `result_id` 重复提交即覆盖
  - 出参：review_id 与对应的人工/Judge 分、系统归因
- `GET /api/manual-review/accuracy`
  - 出参：Judge 准确率（分差 < 0.1 算一致）、归因准确率，附逐条比对明细

### 红队用例（加分项）

- `GET /api/redteam`：查询红队用例（可按攻击类型筛选）
- `GET /api/redteam/{id}`：红队用例详情
- `POST /api/redteam`：创建红队用例（同时写一条 `redteam` 分组的评测用例）
- `PUT /api/redteam/{id}`、`DELETE /api/redteam/{id}`：更新 / 删除
- `GET /api/eval/task/{id}/redteam-report`：红队拦截率统计

## 8. 评分器设计

> 各评分器是否参与 PASS/FAIL 判定、阈值多少，见 [设计决策 D2](设计决策.md#d2-pass--fail-判定规则)；用例如何声明期望，见 [D3](设计决策.md#d3-用例的规则字段)。

### 规则评分器

按用例的 `match_type` 分派，二值 1.0 / 0.0：

- **精确匹配 `EXACT`**：trim 后与 `expected_output` 完全一致
- **正则匹配 `REGEX`**：Java `Pattern.matches` 全串匹配
- **JSON Schema `JSON_SCHEMA`**：输出解析为 JSON 后校验 `expected_output` 中的 Schema；解析失败记 0.0
- **`NONE`**：不产生规则评分

### 工具调用评分器

- **对比逻辑**：提取 Trace 中全部 `TOOL_CALL` span 的 `tool_name`，按 `start_time` 升序展平（嵌套调用一并展平，忽略层级），与 `expected_tools` 对比
- **评分规则**：
  - 完全匹配（顺序一致）：1.0
  - 工具多重集合一致但顺序不同：0.8
  - 其余：`LCS(期望, 实际) / max(长度)`，按比例扣分
- **判定**：≥ `evallab.eval.tool-correctness-threshold` 通过，默认 0.8（区间划分的理由见 [D2](设计决策.md#d2-pass--fail-判定规则)）
- **归因依据**：分数 < 0.5 归"工具调用错误"，0.5 ~ 阈值之间归"规划错误"

### LLM-as-Judge 评分器

- **实现**：Spring AI ChatClient 手工装配（`OpenAiApi` + `OpenAiChatModel`，不走 starter 自动配置），`base_url` 为空时整个 LLM 链路不注册
- **输入**：用例输入 + 期望输出 + 实际 Trace 输出；只有声明了 `expected_output` 的用例才产生 Judge 分
- **Prompt 模板**（实现见 `OpenAiJudgeModel`，换行压成 `\n` 避免多行输出对不齐）：
  ```
  你是一名严格的 Agent 输出评测专家。请从相关性、正确性、完整性三个维度，
  对比「期望输出」评价「实际输出」的质量，给出 0 到 1 之间的分数：
  1.0 表示与期望等价且信息完整，0.0 表示完全错误或答非所问。

  只返回 JSON，不要任何解释性文字或 Markdown 代码块：
  {"score": 0.85, "reason": "一句话说明扣分点"}
  ```
- **失败处理**：调用失败、返回空或非 JSON 时只记 warn 日志并跳过该用例的参考分，不判整轮评测失败；分数越界按 0 / 1 截断
- **定位**：参考型评分器，**不参与 PASS/FAIL 判定**（见 [设计决策 D2](设计决策.md#d2-pass--fail-判定规则)）；红队用例改用确定性守卫正则，同样不用 Judge（见 [D5](设计决策.md#d5-红队防御用确定性守卫正则而非-judge)）
- **校准**：人工抽检计算准确率（分数差 < 0.1 视为一致）

## 9. 失败归因分层

### 5 层归因规则

1. **输入理解错误**
   - 特征：Agent 未正确解析用户指令
   - 检测：实际执行的第一个工具既不是期望的第一个、也不在期望集合内
   - 示例：用户说"计算 3+5"，Agent 理解成"查询天气"

2. **规划错误**
   - 特征：步骤遗漏或顺序错误
   - 检测：工具调用评分落在 `[0.5, 阈值)` 区间（顺序对但缺步骤，或调用了无关工具）
   - 示例：多步计算任务只执行了一步

3. **工具调用错误**
   - 特征：工具参数错误或 API 调用失败
   - 检测：span.error 非空，或工具调用评分 < 0.5
   - 示例：HTTP 500、参数类型错误

4. **输出生成错误**
   - 特征：格式错误或内容不完整
   - 检测：输出不符合 JSON Schema，或明显截断
   - 示例：返回 `{"result":` 未闭合

5. **数据/环境问题**
   - 特征：依赖服务不可用、数据缺失
   - 检测：Trace 状态为 `TIMEOUT`，或任一 span 的 `error` 含 "timeout"、"connection refused"、"unknown host" 等关键词
   - 示例：数据库连接失败

### 归因优先级

按顺序检查，匹配第一个即停止：
1. 数据/环境问题（最底层）
2. 工具调用错误
3. 输入理解错误
4. 规划错误
5. 输出生成错误
6. 未分类（UNKNOWN）

## 10. 回归门禁设计

### 对比指标

1. **通过率**：`passed_cases / total_cases`
2. **平均分**：所有评分的均值（0-1）
3. **P95 耗时**：排序后第 95 百分位的 duration_ms

### 阈值配置

```json
{
  "pass_rate_threshold": -0.10,     // 通过率下降超过 10% 拦截
  "avg_score_threshold": -0.15,     // 平均分下降超过 0.15 拦截
  "p95_duration_threshold": 1.5     // P95 耗时增加 50% 拦截
}
```

### HTTP 接口

**请求**：`POST /api/eval/gate`
```json
{
  "task_id": "current-task-uuid",
  "baseline_id": "baseline-uuid",
  "thresholds": { ... }
}
```

**响应**：通过 200，回归 422，两者响应体结构相同（不套 `Result<T>`）
```json
{
  "passed": false,
  "reason": "通过率下降 15.0%（0.85 -> 0.70），超过阈值 10.0%",
  "changes": {
    "pass_rate": {
      "label": "通过率",
      "baseline_value": 0.85,
      "current_value": 0.70,
      "delta": -0.15,
      "ratio": null,
      "threshold": -0.10,
      "regressed": true,
      "detail": "通过率下降 15.0%（0.85 -> 0.70），超过阈值 10.0%"
    },
    "avg_score": { "label": "平均分", "delta": -0.02, "regressed": false, "...": "..." },
    "p95_duration_ms": { "label": "P95 耗时", "ratio": 1.08, "regressed": false, "...": "..." }
  },
  "task_id": "373448022576730112",
  "baseline_id": "373424401737191424",
  "cross_agent": false
}
```

- `changes` 按指标名索引；通过率与平均分给 `delta`（绝对差值），P95 给 `ratio`（倍数）
- 指标缺失（如基线当时无评分记录、基线 P95 为 0）时该项 `regressed = false`，`detail` 说明「跳过」
- 基线与当前任务的 `agent_name` 不同时 `cross_agent = true`，结论仅供参考

### 命令行工具

```bash
java -jar cli/target/cli.jar \
  --task current-task-uuid \
  --baseline baseline-uuid \
  --threshold-pass-rate -0.10
```

**退出码**：
- 0：通过
- 1：失败（指标退化）
- 2：参数错误或任务不存在

## 11. 简历指标体系

| 指标 | 定义 | 采集方式 | 目标值 |
|------|------|----------|--------|
| **归因准确率** | 系统归因与人工标注一致的比例 | `COUNT(system_failure_category = human_failure_category) / COUNT(*) FROM eval_manual_review` | > 80% |
| **Judge 准确率** | Judge 与人工评分一致的比例（差值 < 0.1） | `COUNT(ABS(human_score - judge_score) < 0.1) / COUNT(*) FROM eval_manual_review` | > 75% |
| **回归检出率** | 故意注入的退化被拦截的次数 | 手动注入 3 次退化，记录 `is_regression_detected = true` 的任务数 | 3/3 (100%) |
| **单次评测耗时** | 10 个用例的评测任务完成时间 | `AVG(TIMESTAMPDIFF(SECOND, created_at, completed_at)) FROM eval_task WHERE total_cases = 10` | < 5 分钟 |
| **接入 Agent 数** | 平台已接入的 Agent 数量 | 手动统计 | ≥ 2 |
| **红队拦截率** | 红队用例中 Agent 防御成功的比例 | `COUNT(status = 'PASS') / COUNT(*) WHERE testcase_id IN (SELECT case_id FROM eval_redteam_case)` | > 60% |

**最终以实测值为准，不预设具体数字**
