# 实测指标

> 记录各阶段验收时的真实运行结果，作为后续回归的基线。数据来自本地 Docker Compose 环境，非估算。

## 阶段 3：LLM-as-Judge 与失败归因

### 环境

| 项 | 值 |
|----|-----|
| 被测 Agent | `fault-injection-agent`（确定性模拟工作流） |
| Judge 模型 | DeepSeek V4.1 Flash（OpenAI 兼容端点） |
| Judge 温度 | 0 |
| 用例数 | 10（5 正常 + 5 故障） |
| 抽检样本 | 2 轮任务共 20 条结果 |

### 归因准确率

**20 / 20 = 100%**

5 类故障均被正确分层，无一误判：

| 用例 | 期望归因 | 系统归因 | 结果 |
|------|----------|----------|------|
| `fault-timeout` | 数据/环境问题 | ENVIRONMENT | ✅ |
| `fault-tool-error` | 工具调用错误 | TOOL_CALL | ✅ |
| `fault-input-misunderstand` | 输入理解错误 | INPUT_MISUNDERSTAND | ✅ |
| `fault-step-missing` | 规划错误 | PLANNING | ✅ |
| `fault-output-format` | 输出生成错误 | OUTPUT_GENERATION | ✅ |
| 5 个正常用例 | 通过，无归因 | null | ✅ |

归因器刻意不读 `fault_injection`，只依据 Trace 与评分结果判定，因此该准确率对真实 Agent 同样成立（前提是故障模式落在 5 层的定义范围内）。

### Judge 准确率

**10 / 12 = 83.3%**（判定口径：|Judge 分 − 人工分| < 0.1 为一致）

12 条有 Judge 分的样本中 10 条一致。两条不一致均为 0.1 分差，恰好卡在严格边界外：

| 用例 | Judge 分 | 人工分 | 分差 |
|------|----------|--------|------|
| `normal-regex` | 0.3 | 0.2 | 0.1 |
| `normal-json-schema` | 0.3 | 0.2 | 0.1 |

这两条本质是「同一判断、不同刻度」，偏差在噪声范围内。目标 75%，实测 83.3%，达标。

`normal-tools-only` 与 4 个故障用例没有 Judge 分：前者未声明 `expected_output`，后者（工具错误、步骤缺失、超时）的 Trace 输出为空或不可评，Judge 无输入依据，故不产生记录。这是设计上的取舍——宁缺毋滥，不用无依据的分数稀释指标。

### 归因覆盖率

**5 / 5 = 100%**（所有失败用例都得到了非 UNKNOWN 的分层）

### 已知局限

- 抽检样本仅 20 条，且来自确定性模拟 Agent，故障模式与归因规则一一对应，准确率偏高是可预期的。真实 Agent 的边界情况（如「理解对了但规划错了」的混合失败）需要更大样本才能暴露。
- Judge 对「格式正确但内容敷衍」的输出评分偏严（`normal-regex` / `normal-json-schema` 都给 0.2~0.3），这是期望行为：这两条用例的判定标准是格式匹配，内容质量本就低于 `normal-exact`。

## 阶段 4：回归门禁

### 环境

| 项 | 值 |
|----|-----|
| 被测 Agent | `fault-injection-agent`，通过 `/admin/degrade` 运行期切换退化模式 |
| 用例数 | 20（`regression` 分组，1-10 为 EXACT + 工具序列，11-20 为仅工具序列） |
| 基线任务 | `373424401737191424`：通过率 1.0000 / 平均分 1.0000 / P95 2110ms |
| 阈值 | 通过率 -0.10、平均分 -0.15、P95 ×1.5（均为默认值） |
| 门禁调用 | `POST /api/eval/gate` 与 `java -jar evallab-cli.jar` 各调一次 |

用例拆成「带输出校验」和「仅工具校验」两组，是为了让三种退化各自只打中一项指标：
`BAD_OUTPUT` 改坏输出，让 11-20 的规则分不参与、只拉低平均分；`FAIL_STATUS` 只改状态，
单独压低通过率；`SLOW` 只加耗时。否则一次退化会同时压低通过率与平均分，三项指标互相污染。

### 回归检出率

**3 / 3 = 100%**（三次退化全部返回 HTTP 422、`is_regression_detected = true`、CLI 退出码 1）

| # | 注入方式 | 指标变化 | 门禁结论 | CLI 退出码 |
|---|----------|----------|----------|------------|
| 1 | `FAIL_STATUS` 作用于 3 个用例 | 通过率 1.0000 → 0.8500（-15.0%） | 422，`通过率下降 15.0%…超过阈值 10.0%` | 1 |
| 2 | `BAD_OUTPUT` 作用于 10 个仅工具校验用例 | 平均分 1.0000 → 0.7588（-0.2412 分） | 422，`平均分下降 0.2412 分…超过阈值 0.15` | 1 |
| 3 | `SLOW` delay 2000ms | P95 2110ms → 4109ms（+94.7%） | 422，`P95 耗时增加 94.7%…超过阈值 50.0%` | 1 |

对照组：同一基线、无退化的干净任务（通过率 1.0000 / 平均分 1.0000 / P95 2288ms）门禁返回 **HTTP 200**，CLI 退出码 0。
放宽 P95 阈值到 3.0 后，第 3 次退化同样放行（退出码 0），说明拦截来自阈值比较本身而非固定失败。

### 单次评测耗时

20 个用例、每次全新任务：

| 用途 | 任务数 | 端到端耗时 |
|------|--------|------------|
| 干净基线 | 4 | 36–40 s |
| 退化任务 | 3 | 36–39 s（`SLOW` 注入那次 76 s） |

均远低于 5 分钟目标。10 用例配置下阶段 3 实测约 22 s。

### CLI 退出码覆盖

| 场景 | 退出码 |
|------|--------|
| 门禁通过 | 0 |
| 检测到回归 | 1 |
| `--task` 不存在（HTTP 404） | 2 |
| 非法阈值（HTTP 400） | 2 |
| 基线不存在（HTTP 404） | 2 |
| 参数缺失 / 未知参数 / 非数字 ID | 2 |

### 已知局限

- 三次退化都由 `fault-injection-agent` 的运行期开关制造，指标变化幅度可控，因此检出率高是设计内的结果。真实 Agent 的退化往往是「部分用例轻微变差」，是否越界取决于阈值设置，需要按项目调参。
- 基线记录的是单一任务的快照，没有做多轮取均值；单次任务的抖动（尤其是 P95）会直接进入基线。用例数越多越稳定，20 个用例时 P95 在干净运行间的波动约 ±10%。
