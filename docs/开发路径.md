# 开发路径

> 目标：先跑通基础闭环（Trace + 用例 + 评分），再做核心亮点（归因 + Judge + 回归门禁），最后沉淀可验证的简历指标。
> 原则：每一步都有可运行产物，故障注入 Agent 先行，确保归因和回归检出可被确定性验证。

## 已定案的设计决策

设计口子已陆续定案，详见 [设计决策.md](设计决策.md)：

| 编号 | 决策 | 落地节点 |
|------|------|----------|
| D1 | 接入主路径为平台拉取 `/execute`，`POST /api/trace` 为补充上报 | 阶段 1 写入 `TRACE_CONTRACT.md`，阶段 2 实现 |
| D2 | PASS ⇔ 全部判定型评分器（RULE、TOOL_CORRECTNESS）达标，Judge 为参考型 | 阶段 2 执行引擎 |
| D3 | 用例以 `match_type` + `expected_output` + `expected_tools` 声明期望 | 阶段 2 建表与评分器 |
| D4 | 归因只依据 Trace 与评分证据，不读 `fault_injection` | 阶段 3 归因器 |

## 阶段 1：Spring Boot 骨架 + Trace 契约

### 目标

先得到一个能启动、能接收 Trace、能访问接口文档的空业务系统，并锁定 Trace 接入契约。

### 任务

- 初始化 Spring Boot 3.5.1 工程（Java 21）
- 建立模块化分包：`api / core / infra / cli`
- 配置 MyBatis-Plus 3.5.9 和 MySQL 连接
- 实现统一返回体（`Result<T>`）
- 实现统一异常处理（`@RestControllerAdvice`）
- 接入 springdoc-openapi（OpenAPI 3）
- 创建 `eval_trace` 和 `eval_span` 表
- 实现 Trace 采集接口：`POST /api/trace`（补充上报路径，`trace_id` 幂等）
- **锁定 Trace 接入契约**：编写 `docs/TRACE_CONTRACT.md`，按 [D1](设计决策.md#d1-两个接入流程的主次) 定死主次（拉取为主、上报为辅）、Agent 响应格式、超时与失败处理、`fault_injection` 参数
- 实现故障注入 Agent（Java，支持 5 种故障类型），暴露 `/execute`

### 产出

```text
GET /actuator/health
GET /v3/api-docs
POST /api/trace
```

### 验收

- 应用可启动，OpenAPI 文档可访问

- 向平台上报一个正常 Trace 和一个故障 Trace，数据正确存入数据库
- `docs/TRACE_CONTRACT.md` 包含完整接口定义和示例

## 阶段 2：用例管理 + 规则评分 + 工具调用评分

### 目标

完成用例 CRUD、执行引擎、两种基础评分器，跑通第一个评测闭环。

### 任务

- 创建 `eval_testcase` 和 `eval_testcase_group` 表（字段按 [D3](设计决策.md#d3-用例的规则字段) 定义）
- 创建 `eval_task`、`eval_result`、`eval_score` 表
- 实现用例管理接口（CRUD + 分组）
- 实现规则评分器（按 `match_type` 分派：精确匹配、正则、JSON Schema）
- **实现工具调用评分器**：对比 `expected_tools` 与 Trace 中 span 的 tool_name 序列
- 实现 PASS/FAIL 判定（按 [D2](设计决策.md#d2-pass--fail-判定规则) 聚合判定型评分器）
- 实现评测任务执行引擎（线程池异步执行，按 [D1](设计决策.md#d1-两个接入流程的主次) 拉取 Agent 并记录失败）
- 实现评测任务查询接口
- 准备 10 个测试用例（5 个正常 + 5 个故障注入）
- 前端：Vue 3 脚手架 + Element Plus
- 前端：用例列表页 + 评测任务页

### 明确不做

- 复杂的用例模板系统
- 用例批量导入导出（第一版手动创建）
- 用例执行历史版本对比

### 产出

- `GET /api/testcase`：查询用例
- `POST /api/testcase`：创建用例
- `POST /api/eval/task`：创建评测任务
- `GET /api/eval/task/{id}`：查询任务状态
- 前端用例管理页面
- 前端评测报告页面（表格展示）

### 验收

- 接入故障注入 Agent，执行 10 个用例
- 规则评分通过率：正常用例 100%，故障注入用例 0%
- 工具调用评分器：检测到工具序列不匹配（目标值：100% 检出）
- 前端可查看用例列表和评测结果
- Docker Compose 一键启动（MySQL + Server + Web），30 秒内服务就绪

## 阶段 3：LLM-as-Judge + 失败归因

### 目标

完成第一个核心亮点：LLM-Judge 评分和 5 层失败归因，并通过人工抽检校准准确率。

### 任务

- 配置 Spring AI 1.1.0 ChatClient（base_url 可配置，支持 OpenAI 兼容接口）
- 实现 LLM-Judge 评分器
  - 设计 Prompt 模板（参考 DeepEval G-Eval）
  - 输入：任务输入 + 期望输出 + 实际输出
  - 输出：0-1 分数 + 理由
- 实现失败归因器（5 层分类规则 + 工具调用评分器联动）
  - 输入理解错误
  - 规划错误
  - 工具调用错误（依据工具调用评分 < 0.5）
  - 输出生成错误
  - 数据/环境问题
- 创建 `eval_manual_review` 表（增加 `human_failure_category` 字段）
- 实现人工抽检接口
- 实现准确率计算接口
  - Judge 准确率：分数差 < 0.1 视为一致
  - 归因准确率：系统归因与人工标注一致的比例
- 前端：评测报告增强
  - 显示 Judge 评分和理由
  - 显示失败分层饼图（ECharts）
- 前端：人工抽检页面

### 产出

- Judge 评分器运行日志
- 归因规则代码（`AttributorService.java`）
- `POST /api/manual-review`：提交人工抽检
- `GET /api/manual-review/accuracy`：查询准确率
- 前端 ECharts 归因饼图

### 验收

- Judge 评分与规则评分同时运行，结果存入 `eval_score`（0-1 量纲）
- 失败用例自动归因，覆盖率目标 > 90%（实际以运行结果为准）
- 人工抽检至少 20 条，计算 Judge 准确率和归因准确率
- 前端显示归因分布饼图和 Judge 理由
- **记录实测 Judge 准确率和归因准确率到 `docs/METRICS.md`**

## 阶段 4：基线 + 回归门禁

### 目标

完成第二个核心亮点：基线管理和回归门禁，支持 HTTP API 和命令行工具两种拦截方式。

### 任务

- 创建 `eval_baseline` 表
- 实现基线创建接口（从评测任务快照）
- 实现回归对比器
  - 计算通过率、平均分、P95 耗时变化
  - 判断是否超过阈值
  - `eval_task` 表增加 `is_regression_detected` 字段
- 实现 HTTP 门禁接口：`POST /api/eval/gate`
  - 通过返回 HTTP 200
  - 失败返回 HTTP 422，body 带变化详情
- 实现命令行工具（`evallab-cli`）
  - 参数：task_id、baseline_id、阈值配置
  - 退出码：0（通过）/ 1（失败）
  - 输出：变化详情（表格格式）
- 编写 GitHub Actions 示例 workflow
  - 运行评测任务
  - 调用门禁 API
  - 失败时评论 PR
- 前端：基线管理页面
- 前端：回归对比结果展示

### 产出

- `POST /api/baseline`：创建基线
- `GET /api/baseline`：查询基线列表
- `POST /api/eval/gate`：回归门禁
- `evallab-cli.jar`：命令行工具
- `.github/workflows/eval-gate.yml`：GitHub Actions 示例

### 验收

- 创建基线，修改 Agent 逻辑（故障注入开关），回归评测拦截
- 门禁接口返回 HTTP 422，body 带失败信息
- 命令行工具返回退出码 1，CI 脚本 `|| exit 1` 拦截
- **手动注入 3 次退化（通过率 -15%、平均分 -0.2、P95 耗时 +50%），记录门禁拦截次数**
- 连续 3 次回归评测，每次耗时目标 < 5 分钟（10 个用例）
- **记录实测回归检出率（3/3）和单次评测耗时到 `docs/METRICS.md`**

## 面试重点讲清

### 技术亮点

- **为什么用两层 Trace 模型（trace > span）而不是三层（trace > span > event）？**
  - 简化查询，events 并入 span JSON，减少表关联
  - 对比 Langfuse 的三层模型，解释取舍

- **为什么工具调用评分器必须先于归因器？**
  - 归因器依赖工具调用评分结果（< 0.5 归为工具调用错误）
  - 展示评分器和归因器的联动设计

- **为什么 LLM-as-Judge 需要人工抽检校准？**
  - Judge 可能过于宽松或严格
  - 人工抽检计算准确率，调整 Prompt 模板
  - 展示校准前后的准确率变化

- **为什么回归门禁用退出码 1 而不是 HTTP 200？**
  - CI 脚本依赖退出码判断成功/失败
  - HTTP 200 无法触发 CI 拦截
  - 展示 GitHub Actions 集成示例

- **如何保证故障注入 Agent 的确定性？**
  - 每种故障类型有明确的触发逻辑
  - 归因规则与故障类型一一对应
  - 验收标准用故障注入覆盖所有归因分层

### 实测指标

- 归因准确率：_X%_（目标 > 80%）
- Judge 准确率：_Y%_（目标 > 75%）
- 回归检出率：3/3（目标 100%）
- 单次评测耗时：_Z_ 分钟（目标 < 5 分钟）
- 接入 Agent 数：3（目标 ≥ 3）
- 红队拦截率：_W%_（目标 > 60%，如果做了）

### 设计决策

- **为什么不用 Redis？**
  - 初期用例量 < 10k，MySQL 性能足够
  - 避免增加部署复杂度
  - 预留扩展点（任务状态存 Redis 的接口已抽象）

- **为什么评分统一用 0-1 量纲？**
  - 便于对比不同评分器结果
  - 人工抽检一致性阈值统一（差值 < 0.1）
  - 展示评分标准化设计

- **为什么用例分组只做单层？**
  - 避免树形结构复杂度
  - 初期用例量不需要多层分组
  - 展示取舍思路（需求 vs 复杂度）

## 建议分支与提交策略

- 开发主干使用 `main`
- 每个阶段可以建短期功能分支，例如 `feature/trace-collection`、`feature/llm-judge`
- 每完成一个可运行闭环就合并回 `main`
- 提交粒度按功能划分，避免巨型提交
- 提交信息格式见 [AGENTS.md](../AGENTS.md)
